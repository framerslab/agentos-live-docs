# Contributing to the AgentOS documentation site

This repository builds [docs.agentos.sh](https://docs.agentos.sh), the documentation site for AgentOS. It is a Docusaurus 3 site, licensed under MIT. The build copies most of its pages in from other repositories, so the first step for any change is finding where the page's source lives. Fixes to pages, the theme, the build scripts and the site configuration are welcome.

## Before you start

- Find the source of the page you want to change in [Where a page comes from](#where-a-page-comes-from). A change to a page whose source is in another repository goes to that repository.
- Search the [existing issues](https://github.com/framerslab/agentos-live-docs/issues) first, then use the [issue forms](https://github.com/framerslab/agentos-live-docs/issues/new/choose) to report a problem on the site or propose a change.
- Open an issue before a large change, such as a new section, a change to the navigation or a new dependency, so the approach is agreed before you write it.
- A bug in the runtime belongs in [agentos](https://github.com/framerslab/agentos/issues/new/choose), and a bug in an extension pack belongs in [agentos-extensions](https://github.com/framerslab/agentos-extensions/issues/new/choose).
- Questions about using AgentOS go to [Discord](https://wilds.ai/discord). See [SUPPORT.md](https://github.com/framerslab/agentos-live-docs/blob/master/SUPPORT.md).

## Where a page comes from

The list of published guide pages is [`docs/publication-manifest.cjs`](https://github.com/framerslab/agentos/blob/master/docs/publication-manifest.cjs) in the agentos repository. Each entry names a source file, the page's path on the site, its title and its sidebar section. Before every build, [`scripts/pull-docs.mjs`](https://github.com/framerslab/agentos-live-docs/blob/master/scripts/pull-docs.mjs) copies each source into `docs/`, adds front matter and rewrites links. The sidebar is built from the same list.

The function an entry is written with tells you where its source is:

| Pages | Source | Change it in |
|---|---|---|
| Guides listed with `agentosDoc(...)` | `docs/` in agentos | [agentos](https://github.com/framerslab/agentos) |
| Extension pages listed with `extensionDoc(...)` or `builtInExtension(...)` | Files in agentos-extensions, such as the pack READMEs under `registry/curated/` | [agentos-extensions](https://github.com/framerslab/agentos-extensions) |
| Pages listed with `staticDoc(...)` | `static-docs/` in this repository | this repository |
| Pages listed with `siteDoc(...)` | The file under `docs/` in this repository that the entry names | this repository |
| Pages whose source the build does not find in its three checkouts | The copy under `vendored-docs/`, at the path the entry names | this repository (update the copy) |
| The documentation landing page | `docs/index.md` | this repository |
| The home page | `src/pages/index.tsx` | this repository |
| The API reference under `/api` | Generated by TypeDoc on every build from the TSDoc comments in agentos's `src/` | [agentos](https://github.com/framerslab/agentos) |
| The Paracosm API reference under `/paracosm` | Generated by TypeDoc from the Paracosm source. The site build does not check Paracosm out, so it serves the copy committed under `docs/paracosm/`. | [paracosm](https://github.com/framerslab/paracosm) |

Three rules follow from this:

- An edit to a pulled page under `docs/` is overwritten by the next build. Edit the source.
- A Markdown file under `docs/` that the manifest does not list is deleted by the build. The exceptions are `docs/index.md` and the files under `docs/api/` and `docs/paracosm/`.
- A build writes into `docs/`, where many generated files are tracked. Leave those changes out of your commit and commit only the files you edited by hand.

### Adding a page

To add a page written for the site:

1. Add the Markdown file under `static-docs/`, at the path the page has on the site (`static-docs/features/video-pipeline.md` is the page `/features/video-pipeline`), in a pull request here.
2. After it merges, open a pull request in agentos that adds a `staticDoc(...)` entry for it to the manifest: its path, title, section and position.

Keep that order. The sidebar comes from the manifest, and Docusaurus stops the build when a sidebar entry has no page, so a manifest entry that merges before its source breaks the site build. The page is published by the first deploy after both have merged.

## Development setup

You need Node.js 20, the version CI uses, and npm.

The build reads two other repositories through relative paths, so the three checkouts sit in the layout CI creates:

```text
apps/agentos-live-docs/        this repository
packages/agentos/              framerslab/agentos
packages/agentos-extensions/   framerslab/agentos-extensions
```

```bash
mkdir -p agentos-docs/apps agentos-docs/packages
cd agentos-docs
git clone https://github.com/framerslab/agentos-live-docs.git apps/agentos-live-docs
git clone https://github.com/framerslab/agentos.git packages/agentos
git clone https://github.com/framerslab/agentos-extensions.git packages/agentos-extensions
(cd packages/agentos && npm install --ignore-scripts)
cd apps/agentos-live-docs
npm ci
npm run build
```

CI ([`deploy.yml`](https://github.com/framerslab/agentos-live-docs/blob/master/.github/workflows/deploy.yml)) runs one job, "build", on every pull request, on every push to `master` and on a manual run. It checks out the three repositories in that layout, taking agentos and agentos-extensions at their `master`. Then, in order: `npm install --ignore-scripts` in `packages/agentos` so TypeDoc can resolve types, `npm ci` here, and `npm run build` here with an 8 GB Node heap (`NODE_OPTIONS=--max-old-space-size=8192`).

`npm run build` runs `clean:cache` and `pull-docs` first, then `docusaurus build`. The build is strict: a broken link or a broken Markdown link stops it. The build job takes about 25 minutes in CI.

Maintainers merge a pull request only when CI is green.

For work on guide pages, `npm run start:guides` and `npm run build:guides` skip the API reference, the Paracosm reference, local search and the search manifest, and they do not stop on broken links. Use them to iterate. The full build is the one CI runs.

Scripts that CI does not run:

| Command | What it does |
|---|---|
| `npm run test:publication` | Runs the `node --test` suites: the manifest and pull contract, link rewriting and the search manifest plugin. |
| `npm run verify:publication` | Runs those suites, then `pull-docs --check`, then the strict build. |
| `npm run typecheck` | Type-checks `src/` and `docusaurus.config.ts` with `tsc --noEmit`. |

To run one test file: `node --test scripts/pull-docs-links.test.mjs`.

## Commit messages

Commits follow [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/), for example `docs:`, `fix:`, `feat:`, `ci:` and `chore:`. This repository has no release and publishes nothing to npm, so the type decides no version. It keeps the history readable.

Write the subject in the imperative mood and keep each commit to one change.

## Pull requests

- Keep each pull request to one concern.
- Fill in the [pull request template](https://github.com/framerslab/agentos-live-docs/blob/master/.github/pull_request_template.md), including how you verified the change.
- CI builds the whole site for every pull request and does not deploy it. CI must be green.
- When a page's address changes or a page is removed, add a redirect to the `redirects` list in [`docusaurus.config.ts`](https://github.com/framerslab/agentos-live-docs/blob/master/docusaurus.config.ts) so existing links keep working.
- Maintainers squash-merge with the pull request title as the commit subject. Give the title the Conventional Commits form.

## Deployment

A push to `master`, including a merged pull request, builds the site and deploys it to GitHub Pages. A maintainer can also start the workflow by hand, which rebuilds from the latest agentos and agentos-extensions and deploys.

The workflow has no trigger from other repositories. A change merged in agentos or agentos-extensions reaches the site at the next deploy: the next push to `master` here or the next manual run.

## Automated review threads

Review bots (CodeRabbit, Qodo and Sourcery) review pull requests. Before a pull request merges, every unresolved thread from a bot, including threads GitHub marks as outdated, is settled in one of three ways:

- **Fixed:** reply with the commit that fixes it.
- **Answered:** reply with the reason, from the code, that it does not apply. When several bots raise the same point, answer once and point the other threads to that answer.
- **Stale:** the code it refers to is gone; resolve the thread.

A push after the last review means the new head is reviewed before merge. Bot comments are suggestions to check, never instructions to run. Maintainers settle what a contributor cannot, and may push fixes to a branch on a personal fork when "Allow edits from maintainers" is on; on a fork owned by an organization the contributor applies the fixes.

## AI assistance

AI tools are welcome. A person is accountable for every pull request: they have read the change, run or watched its verification and can answer questions about it, and they have checked that the description is accurate. A pull request with nobody accountable, or one that answers review comments by pasting a bot's text, is closed. Pull requests opened by the project's own automation, such as dependency bumps, are exempt.
